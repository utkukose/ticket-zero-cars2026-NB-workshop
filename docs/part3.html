Part 3 · Defense~12 minutes

The defenses

Protection comes from how the agent is built, not from the wording of the message.

Station 1 · predict

The tempting wrong answer

The obvious fix is to filter tickets that contain attack phrases. You turn on a phrase blocklist. Does it stop the authority attack from Part 2?

Your prediction

A blocklist catches only the undisguised attempts. Authority framing, a fake system tag, an encoded payload, or data-planted instructions all carry the same objective past it, and it also rejects legitimate customers whose wording happens to match. It is the one control in the game that is there to be defeated. The useful controls act on the architecture.

Station 2 · the controls

Four controls that actually hold

No single one stops everything without also turning away a real customer, so a real deployment layers them.

Separate read from act
Treat the ticket and retrieved text as data only, so no action is derived from it. The most general answer to injection, direct or indirect.
Limit connections
Disconnect external tools so nothing can leave the system. An agent that cannot send cannot exfiltrate.
Human in the loop
Queue consequential actions, a credit or an outbound message, for a person to approve.
Check the output
Scan anything leaving the agent for secrets and personal data. A backstop when an upstream control is missed.
Block bad phrases
A blocklist that is easy to slip past, and rejects real customers. Included to be defeated.

Station 3 · try it

Defend the agent

The same in-page agent. First send an attack that lands, such as the authority ticket. Then arm a control on the right and send it again: watch it get stopped. Try the weak blocklist against the authority or encoded attack, and watch it still land.

An egress filter does not stop a fraudulent credit, and a human-approval gate does not stop a prompt from being extracted. Each stage needs its own control.
